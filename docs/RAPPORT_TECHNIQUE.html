1. Vue d'ensemble

ClearNet est un moteur de compensation décentralisée : les entreprises échangent des créances et des dettes bilatérales, et le système calcule et exécute une compensation nette (netting) — sans mouvement de trésorerie systématique. Le registre des positions nettes est porté par une blockchain (Ethereum, testnet Sepolia), les transactions sont servies par une API NestJS adossée à un graphe Neo4j, et le tout est packagé pour le déploiement cloud (Docker Compose en dev, Helm en production).

Les transactions sont créées côté API (persistance Neo4j) puis, si le pont est activé (ONCHAIN_ENABLED=true), réglées en arrière-plan sur le CompensationEngine (netting de positions, sans transfert ERC20). Le backend agit comme opérateur admin du moteur de compensation : il enregistre les positions nettes et exécute les règlements avec la même clé que le déploiement des contrats.

4. Backend NestJS — analyse détaillée

4.1 Bootstrap et conventions (main.ts)

  • Préfixe global /api ; CORS ouvert (origin: true, credentials: true).
  • ValidationPipe strict : whitelist + transform + forbidNonWhitelisted — les champs inconnus rejettent la requête.
  • Rate limiting global via ThrottlerModule : 100 requêtes / 60 s par défaut (THROTTLE_TTL, THROTTLE_LIMIT), appliqué par RateLimitGuard (APP_GUARD).
  • Log de démarrage affichant le régime de rate-limit et l'état du pont (BLOCKCHAIN_ENABLED).
  • ConfigModule.forRoot({ isGlobal: true }) — toutes les variables d'environnement sont lues à travers ConfigService.

4.4 Persistance Neo4j

  • Driver neo4j-driver 5.8 injecté en singleton global (NEO4J_DRIVER), fermé au shutdown de l'application.
  • Schéma de base : (User {email, name, passwordHash, …}) -[:SENT]-> (Transaction {id, amount, note, createdAt, onchainHash?, onchainStatus?, onchainError?}) <-[:RECEIVED]- (User) ; nœuds Company {name, industry, country, address}.
  • Identifiants de transaction par randomUUID() côté Cypher ; historique trié par createdAt DESC.
  • Depuis V1.2, le nœud Transaction reçoit onchainHash (hash du settle) et onchainStatus = SUCCESS ou FAILED (+ onchainError).

4.5 Sécurité applicative

  • Mots de passe : bcryptjs, 10 rounds, hash seul stocké.
  • Session : JWT (Bearer) avec JwtAuthGuard sur les routes privées ; identité reconstruite via @CurrentUser().
  • Validation : DTO class-validator + ValidationPipe strict (rejet des champs inconnus).
  • Rate limiting : global 100 req/60 s + limite renforcée sur auth (5/60 s login, 10/60 s register) et surcharge possible par décorateur @Throttle.
  • Clés et secrets : exclusivement via variables d'environnement (JWT_SECRET, DEMO_API_KEY, clés oracles, clé privée blockchain) ; défauts uniquement en dev (docker-compose), jamais en production (Helm → secrets).
  • Conformité : ItarGuard / OfacGuard disponibles, actifs selon flag (cf. §8).

4.6 Services clés — détails d'implémentation

TransactionsService — règlement on-chain (V1.2)

  • Vérifie l'auto-transfert et la conformité ITAR/OFAC avant toute persistance.
  • Persiste la transaction, puis déclenche (si ONCHAIN_ENABLED=true) un règlement fire-and-forget : la réponse HTTP n'est jamais bloquée.
  • processOnChainSettlement appelle BlockchainService.settleCompensation(fromEmail, toEmail, amount) ; succès → onchainHash + SUCCESS ; échec → FAILED + message, la transaction reste valide hors-chaîne.
  • Les adresses on-chain sont dérivées des emails (keccak256, cf. §5.6) : aucune donnée wallet à stocker.

File BullMQ (V1.3) — règlements industrialisés

  • Activation : QUEUE_ENABLED=true (câblage module, off par défaut — fire-and-forget préservé). La décision d'acheminer chaque transaction est évaluée dynamiquement (ConfigService, à chaque appel) : désactiver la variable en cours de vie du pod bascule proprement sur le fire-and-forget, sans redémarrage (3.1).
  • Job onchain-settlement : retries exponentielles (QUEUE_ATTEMPTS=5, QUEUE_BACKOFF_MS=5000), removeOnComplete=1000, removeOnFail=5000 ; succès → markOnchainSuccess + événement transaction:status SUCCESS ; échec → markOnchainFailed + événement FAILED + rethrow.
  • Échecs définitifs (3.3) : événement failed du worker → nœud FailedJob d'audit en Neo4j (jobId, queue, txId, error, attemptsMade, failedAt) + notification Slack (SLACK_WEBHOOK_URL, optionnel).
  • Test d'intégration (3.2) : queue.integration.spec.ts — Redis réel, flux create → file → processor → SUCCESS/FAILED (écriture Neo4j) → WebSocket ; actif en CI (service Redis).

ComplianceService — ITAR/OFAC

  • Screening OFAC à 3 niveaux : liste embarquée → CSV optionnel (OFAC_CSV_PATH) → API externe (OFAC_API_KEY) ; source rapportée dans le résultat.
  • ITAR : secteurs Défense/Spatial autorisés uniquement pour les pays de la liste blanche (US, FR, UK, DE, IT, JP, AU).
  • Désactivé → no-op strict (retourne autorisé).

OracleService — données sectorielles

  • Stormglass (maritime) : niveau de mer → demurrageDays (1/3/5 j selon le seuil 1,2 / 2,5 m).
  • Space-Track (spatial) : fenêtre de lancement (60 j par défaut).
  • ClinicalTrials.gov (biotech) : validité d'un jalon via NCT.
  • Chaque appel est borné par ORACLE_TIMEOUT_MS (2,5 s) ; toute erreur → valeur de repli identique au comportement V1.1 + log d'alerte.

ZkProofService — preuves Groth16

  • generateProof(inputs) : import dynamique de snarkjs, lecture de ZK_ARTIFACTS_DIR (*.wasm + *.zkey), construction du témoin avec montants en micro-CLRN (×1e6).
  • Signaux publics dans l'ordre du circuit : [maxAmount, commitment] (corrigé V1.2).
  • verifyProof : vérification off-chain (snarkjs) et on-chain (ABI uint256[2] input).
  • Flag ZK_ENABLED=false → generateProof échoue explicitement, verifyProof → {valid:false} : aucune régression.

GraphService — priorisation de cycle

  • computeUrgency : demurrage réel (si oracles actifs) sinon 3 j ; règle demurrage > 3 j → cycle prioritaire ; la source (oracle/default) est rapportée.

CompaniesService — référentiel sectoriel

  • 15 secteurs (12 V1 + 3 V1.1 : Maritime, Spatial, Biotech), chacun avec libellé, groupe, version et description.
  • CRUD entreprises + countByIndustry (agrégat Cypher) alimentant /industries et /industries/stats.

4.7 Passerelle temps réel — TransactionGateway (V1.3)

  • Namespace /transactions (CORS ouvert), @nestjs/websockets + socket.io.
  • Handshake authentifié : JWT via auth.token ou query.token ; échec → client.disconnect(true).
  • Room par utilisateur user:<email> — aucun client ne reçoit les événements d'un autre compte.
  • Événement transaction:status : PENDING à la création, puis SUCCESS (avec hash) ou FAILED (avec error) après règlement on-chain — fin du « fire-and-forget » silencieux.
  • Rétrocompatibilité : le flux HTTP est inchangé ; le gateway ne fait que diffuser des événements.

5.2 Contrats

ClearNetToken (ERC20 « ClearNet Token », symbole CLRN, 18 décimales)

  • mint(to, amount) — onlyOwner (émission admin).
  • burn(amount) — l'utilisateur brûle ses propres jetons.
  • Hérite d'OpenZeppelin ERC20 + Ownable.

CompensationEngine — moteur de netting (MVP + extension ZK)

  • admin immuable = déployeur ; toutes les écritures sont onlyAdmin.
  • netPositions(address) → int256 : registre de positions nettes.
  • updatePosition(account, delta) : ajustement de position (émission PositionUpdated).
  • settle(from, to, amount) : transfert de position, sans mouvement ERC20 ; invariants : netPositions[from] ≥ amount et netPositions[to] ≤ 0 (le créditeur paie, le débiteur reçoit).
  • setZkSettings(verifier, required, maxAmount) : active l'exigence de preuve ZK (feature flag on-chain, défaut false — comportement V1.1 préservé).
  • settleWithProof(from, to, amount, a, b, c, input[2]) : si zkRequired, exige 0 < amount ≤ maxAmount et une preuve Groth16 valide (IZkVerifier.verifyProof) avant _settle.
  • Événements : PositionUpdated, Compensated, ZkSettingsUpdated.

ChainlinkPriceFeed — oracle de prix on-chain

  • Trois flux Chainlink (ETH/USD, BTC/USD, XAU/USD) déclarés au constructeur (adresses ≠ 0 imposées).
  • Interface AggregatorV3Interface déclarée en dur (aucune dépendance npm).
  • Garde anti-stale : MAX_STALE_AGE = 24 h, round incomplet / réponse ≤ 0 rejetés.
  • Lectures : getEthUsd(), getBtcUsd(), getXauUsd(), getPrices() (batch) et refresh() qui mémorise les prix (lastEthUsd…, lastUpdateAt) pour les lecteurs fréquents.

IZkVerifier (interface)

  • Signature Groth16 : verifyProof(uint256[2] a, uint256[2][2] b, uint256[2] c, uint256[2] input) — 2 signaux publics [maxAmount, commitment], alignée sur le circuit transaction.circom (correction V1.2 : input [1] → [2]).
  • Le vrai Verifier.sol est généré par scripts/generate-zk-keys.sh (circom + snarkjs) — jamais commité.

9. Cycle de vie d'un règlement (bout en bout)

  1. L'utilisateur s'authentifie (JWT) et POST /api/transactions (montant en CLRN, destinataire, note optionnelle).
  2. Le backend vérifie : auto-transfert interdit → compliance (si active) : screening OFAC des deux parties + règle ITAR.
  3. Persistance du nœud Transaction dans Neo4j (relations SENT / RECEIVED, createdAt, onchainStatus vide).
  4. Réponse HTTP 201 immédiate ; en parallèle (si pont actif) : settleCompensation(from, to, amount) sur CompensationEngine.
  5. Le contrat vérifie les invariants de netting (crédit du payeur suffisant, dette de la contrepartie) et ajuste les positions nettes ; événement Compensated.
  6. Écriture onchainHash + onchainStatus: SUCCESS (ou FAILED + onchainError, sans invalider la transaction).
  7. Consultation : GET /api/transactions/history ; diagnostic du pont : GET /api/blockchain/status.

Variante ZK : avec zkRequired=true, l'étape 4 passe par settleWithProof — la preuve est générée par le backend (snarkjs) ou fournie ; le montant est borné par maxAmount. Caveat d'échelle documenté : le circuit raisonne en micro-CLRN (×1e6), le ledger on-chain en wei (×1e18) — le gate valide la mécanique de preuve, l'égalité exacte d'échelle est un raffinement de phase suivante (acceptable sur testnet).

14. Limites connues & perspectives

  • MVP opérateur centralisé : le backend détient la clé admin du CompensationEngine — le netting est exécuté de façon déléguée, pas par un réseau de validateurs.
  • Identités dérivées des emails : adresses déterministes sans registre de correspondance signé ; à remplacer par un schéma d'identité auto-souveraine (DIDs) en phase suivante.
  • Échelle ZK : bornes 64 bits du circuit vs wei du ledger — unalignement documenté.
  • Oracles : clés API à provisionner ; l'agrégation Chainlink on-chain (ETH/BTC/XAU) est déclarée mais non déployée.
  • Multi-réseaux : la config Hardhat prévoit mainnet (clearnet) ; le déploiement réel reste à valider sur Sepolia puis sur le réseau cible.
  • Perspectives : file de règlements avec retries/backoff, surveillance des événements on-chain (indexeur), tests e2e Kubernetes (kind/CI), renforcement du référentiel OFAC (listes mises à jour), vérification de preuves hors-ligne pour les parties.
  • Mobile V1.3 : contrat API aligné (solde, pagination, egonet, socket.io) ; validation sur émulateur Android restant à exécuter (bout-en-bout réel).
