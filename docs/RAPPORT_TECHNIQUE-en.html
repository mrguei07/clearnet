1. Overview

ClearNet is a decentralized clearing engine: companies exchange bilateral receivables and payables, and the system computes and executes a net clearing (netting) — without systematic cash movements. The register of net positions is carried by a blockchain (Ethereum, Sepolia testnet), transactions are served by a NestJS API backed by a Neo4j graph, and everything is packaged for cloud deployment (Docker Compose in dev, Helm in production).

Transactions are created on the API side (Neo4j persistence) and then, if the bridge is enabled (ONCHAIN_ENABLED=true), settled in the background on the CompensationEngine (netting of positions, without ERC20 transfer). The backend acts as the admin operator of the clearing engine: it records net positions and executes settlements with the same key as the contract deployment.

4. NestJS Backend — detailed analysis

4.1 Bootstrap and conventions (main.ts)

  • Global /api prefix; open CORS (origin: true, credentials: true).
  • Strict ValidationPipe: whitelist + transform + forbidNonWhitelisted — unknown fields reject the request.
  • Global rate limiting via ThrottlerModule: 100 requests / 60 s by default (THROTTLE_TTL, THROTTLE_LIMIT), applied by RateLimitGuard (APP_GUARD).
  • Startup log showing the rate-limit regime and the bridge status (BLOCKCHAIN_ENABLED).
  • ConfigModule.forRoot({ isGlobal: true }) — all environment variables are read through ConfigService.

4.4 Neo4j persistence

  • neo4j-driver 5.8 injected as a global singleton (NEO4J_DRIVER), closed on application shutdown.
  • Base schema: (User {email, name, passwordHash, …}) -[:SENT]-> (Transaction {id, amount, note, createdAt, onchainHash?, onchainStatus?, onchainError?}) <-[:RECEIVED]- (User); Company {name, industry, country, address} nodes.
  • Transaction identifiers via randomUUID() on the Cypher side; history sorted by createdAt DESC.
  • Since V1.2, the Transaction node receives onchainHash (settle hash) and onchainStatus = SUCCESS or FAILED (+ onchainError).

4.5 Application security

  • Passwords: bcryptjs, 10 rounds, only the hash is stored.
  • Session: JWT (Bearer) with JwtAuthGuard on private routes; identity rebuilt via @CurrentUser().
  • Validation: class-validator DTOs + strict ValidationPipe (unknown fields rejected).
  • Rate limiting: global 100 req/60 s + reinforced limit on auth (5/60 s login, 10/60 s register) and possible override via the @Throttle decorator.
  • Keys and secrets: exclusively via environment variables (JWT_SECRET, DEMO_API_KEY, oracle keys, blockchain private key); defaults only in dev (docker-compose), never in production (Helm → secrets).
  • Compliance: ItarGuard / OfacGuard available, active depending on the flag (see §8).

4.6 Key services — implementation details

TransactionsService — on-chain settlement (V1.2)

  • Checks self-transfer and ITAR/OFAC compliance before any persistence.
  • Persists the transaction, then triggers (if ONCHAIN_ENABLED=true) a fire-and-forget settlement: the HTTP response is never blocked.
  • processOnChainSettlement calls BlockchainService.settleCompensation(fromEmail, toEmail, amount); success → onchainHash + SUCCESS; failure → FAILED + message, the transaction remains valid off-chain.
  • On-chain addresses are derived from emails (keccak256, see §5.6): no wallet data to store.

BullMQ queue (V1.3) — industrialized settlements

  • Activation: QUEUE_ENABLED=true (module wiring, off by default — fire-and-forget preserved). The decision to route each transaction is evaluated dynamically (ConfigService, on every call): disabling the variable during the pod's lifetime cleanly falls back to fire-and-forget, without a restart (3.1).
  • Job onchain-settlement: exponential retries (QUEUE_ATTEMPTS=5, QUEUE_BACKOFF_MS=5000), removeOnComplete=1000, removeOnFail=5000; success → markOnchainSuccess + transaction:status SUCCESS event; failure → markOnchainFailed + FAILED event + rethrow.
  • Final failures (3.3): worker failed event → FailedJob audit node in Neo4j (jobId, queue, txId, error, attemptsMade, failedAt) + Slack notification (SLACK_WEBHOOK_URL, optional).
  • Integration test (3.2): queue.integration.spec.ts — real Redis, create → queue → processor → SUCCESS/FAILED (Neo4j write) → WebSocket flow; enabled in CI (Redis service).

ComplianceService — ITAR/OFAC

  • 3-level OFAC screening: built-in list → optional CSV (OFAC_CSV_PATH) → external API (OFAC_API_KEY); the source is reported in the result.
  • ITAR: Defense/Spatial sectors authorized only for whitelisted countries (US, FR, UK, DE, IT, JP, AU).
  • Disabled → strict no-op (returns authorized).

OracleService — sector data

  • Stormglass (maritime): sea level → demurrageDays (1/3/5 days depending on the 1.2/2.5 m threshold).
  • Space-Track (space): launch window (60 days by default).
  • ClinicalTrials.gov (biotech): milestone validity via NCT.
  • Each call is bounded by ORACLE_TIMEOUT_MS (2.5 s); any error → fallback value identical to V1.1 behavior + alert log.

ZkProofService — Groth16 proofs

  • generateProof(inputs): dynamic import of snarkjs, reads ZK_ARTIFACTS_DIR (*.wasm + *.zkey), builds the witness with amounts in micro-CLRN (×1e6).
  • Public signals in circuit order: [maxAmount, commitment] (fixed in V1.2).
  • verifyProof: off-chain verification (snarkjs) and on-chain (ABI uint256[2] input).
  • ZK_ENABLED=false flag → generateProof fails explicitly, verifyProof → {valid:false}: no regression.

GraphService — cycle prioritization

  • computeUrgency: real demurrage (if oracles active) otherwise 3 days; rule demurrage > 3 days → priority cycle; the source (oracle/default) is reported.

CompaniesService — sector registry

  • 15 sectors (12 V1 + 3 V1.1: Maritime, Spatial, Biotech), each with a label, group, version and description.
  • Companies CRUD + countByIndustry (Cypher aggregate) feeding /industries and /industries/stats.

4.7 Real-time gateway — TransactionGateway (V1.3)

  • /transactions namespace (CORS open), @nestjs/websockets + socket.io.
  • Authenticated handshake: JWT via auth.token or query.token; failure → client.disconnect(true).
  • Per-user room user:<email> — no client receives events from another account.
  • transaction:status event: PENDING at creation, then SUCCESS (with hash) or FAILED (with error) after on-chain settlement — end of the silent « fire-and-forget ».
  • Backward compatibility: the HTTP flow is unchanged; the gateway only broadcasts events.

5.2 Contracts

ClearNetToken (ERC20 "ClearNet Token", symbol CLRN, 18 decimals)

  • mint(to, amount) — onlyOwner (admin issuance).
  • burn(amount) — the user burns their own tokens.
  • Inherits OpenZeppelin ERC20 + Ownable.

CompensationEngine — netting engine (MVP + ZK extension)

  • Immutable admin = deployer; all writes are onlyAdmin.
  • netPositions(address) → int256: net positions registry.
  • updatePosition(account, delta): position adjustment (PositionUpdated emission).
  • settle(from, to, amount): position transfer, without ERC20 movement; invariants: netPositions[from] ≥ amount and netPositions[to] ≤ 0 (the creditor pays, the debtor receives).
  • setZkSettings(verifier, required, maxAmount): enables the ZK proof requirement (on-chain feature flag, default false — V1.1 behavior preserved).
  • settleWithProof(from, to, amount, a, b, c, input[2]): if zkRequired, requires 0 < amount ≤ maxAmount and a valid Groth16 proof (IZkVerifier.verifyProof) before _settle.
  • Events: PositionUpdated, Compensated, ZkSettingsUpdated.

ChainlinkPriceFeed — on-chain price oracle

  • Three Chainlink feeds (ETH/USD, BTC/USD, XAU/USD) declared in the constructor (non-zero addresses enforced).
  • AggregatorV3Interface declared inline (no npm dependency).
  • Anti-stale guard: MAX_STALE_AGE = 24 h, incomplete round / response ≤ 0 rejected.
  • Reads: getEthUsd(), getBtcUsd(), getXauUsd(), getPrices() (batch) and refresh() which caches the prices (lastEthUsd…, lastUpdateAt) for frequent readers.

IZkVerifier (interface)

  • Groth16 signature: verifyProof(uint256[2] a, uint256[2][2] b, uint256[2] c, uint256[2] input) — 2 public signals [maxAmount, commitment], aligned with the circuit transaction.circom (V1.2 fix: input [1] → [2]).
  • The actual Verifier.sol is generated by scripts/generate-zk-keys.sh (circom + snarkjs) — never committed.

  • api/client.ts: typed fetch wrapper; base URL EXPO_PUBLIC_API_URL otherwise 10.0.2.2:3000/api (Android emulator) otherwise localhost:3000/api.
  • Config plugin plugins/withClearNetNative.js: Android permissions (INTERNET, ACCESS_NETWORK_STATE, storage), usesCleartextTraffic (dev), NSPhotoLibraryUsageDescription (iOS).
  • API contract aligned V1.3: GET /transactions/balance (balance), GET /transactions?page=&limit= (paginated history), GET /graph/egonet (Force Graph), socket.io namespace /transactions (JWT handshake, transaction:status event); sector theme fed by user.industry returned by /auth/login and /auth/register.

9. Lifecycle of a settlement (end to end)

  1. The user authenticates (JWT) and POST /api/transactions (amount in CLRN, recipient, optional note).
  2. The backend checks: self-transfer forbidden → compliance (if active): OFAC screening of both parties + ITAR rule.
  3. Persistence of the Transaction node in Neo4j (SENT / RECEIVED relationships, createdAt, empty onchainStatus).
  4. Immediate HTTP 201 response; in parallel (if the bridge is active): settleCompensation(from, to, amount) on CompensationEngine.
  5. The contract checks the netting invariants (sufficient payer credit, counterparty debt) and adjusts the net positions; Compensated event.
  6. Writes onchainHash + onchainStatus: SUCCESS (or FAILED + onchainError, without invalidating the transaction).
  7. Consultation: GET /api/transactions/history; bridge diagnostics: GET /api/blockchain/status.

ZK variant: with zkRequired=true, step 4 goes through settleWithProof — the proof is generated by the backend (snarkjs) or provided; the amount is bounded by maxAmount. Documented scale caveat: the circuit reasons in micro-CLRN (×1e6), the on-chain ledger in wei (×1e18) — the gate validates the proof mechanics, exact scale equality is a refinement for a later phase (acceptable on testnet).

14. Known limits & outlook

  • Centralized operator MVP: the backend holds the admin key of the CompensationEngine — netting is executed in a delegated way, not by a network of validators.
  • Email-derived identities: deterministic addresses without a signed mapping registry; to be replaced by a self-sovereign identity scheme (DIDs) in a later phase.
  • ZK scale: 64-bit circuit bounds vs ledger wei — documented misalignment.
  • Oracles: API keys to provision; the on-chain Chainlink aggregation (ETH/BTC/XAU) is declared but not deployed.
  • Multi-network: the Hardhat config provides for mainnet (clearnet); the real deployment still needs to be validated on Sepolia then on the target network.
  • Outlook: settlement queue with retries/backoff, on-chain event monitoring (indexer), Kubernetes e2e tests (kind/CI), OFAC registry strengthening (up-to-date lists), offline proof verification for the parties.
  • Mobile V1.3: aligned API contract (balance, pagination, egonet, socket.io); validation on Android emulator still to be executed (real end-to-end).
